## 三、问题、触发条件及排查依据

### R01 [P1] 自动备份从设置页恢复，会被接受后清空业务数据

- 位置：`lib/data-store.js:108–114`、`webapp/js/store.js:718–730`、`:738–747`。
- 触发：从“打开备份目录”取得 `data-latest.json` 或时间快照，再通过设置中的“恢复备份”选择它。
- 原因：自动备份 `data` 保存 `sd_v1_orders` 等原始键与 JSON 字符串；手动恢复期待 `orders`、`customers` 等对象字段。两者却同为 `app: songhuodan`、`version: 1`，入口检查会放行；后续校验允许已知字段全部缺失，恢复又把缺失字段设成空默认值。
- 实测：恢复前 1 个客户、1 个商品、1 张单据；调用恢复未抛错，之后全部变成 0。
- 影响：恢复操作可能覆盖现有业务数据，界面还会提示恢复成功。按原始键自动恢复的启动流程与此不同，不是说自动恢复本身必然失败。
- 建议：区分备份种类并统一版本/模式校验；明确转换原始键结构，或在设置页拒绝该文件。未知结构必须在修改数据前拒绝。

### R02 [P1] 立即备份失败仍返回成功，并丢失后续重试标记

- 位置：`main.js:625–633`、`lib/data-store.js:172–176`、`webapp/js/views/settings.js:252–258`。
- 触发：备份目录不可创建、不可写或磁盘写入失败。
- 原因：`writeBackupMirror()` 用 `false` 表达失败；`sd:backupNow` 忽略 `flushBackup()` 和图片备份的返回值，仍返回 `{ok:true}`。此外 `flushBackup()` 在确认写入成功前就把 `backupDirty` 设为 `false`。
- 实测：使用普通文件占住备份目录路径，IPC 返回 `ok:true`，同时 `info.backupError` 已有明确错误，实际备份不存在。首次 flush 为 `false`，未新增写入时第二次 flush 为 `true`，但没有重新尝试。
- 影响：用户会得到“已备份到程序目录之外”的错误保证；备份仍落后且不会按原计划重试。
- 建议：只有所有必要写入完成后返回成功并清理 dirty 标记；失败保留待重试状态，把原因传回 UI。

### R03 [P1] 只读保护状态仍可成功导出空或不完整报表

- 位置：`webapp/js/store.js:129–146`、`:703`、`:803`、`:828`、`:1017`；`webapp/js/views/settings.js:297`。
- 触发：订单等业务键损坏，加载后 `recoveryState().blocked === true`，再到设置或其他报表入口导出。
- 原因：损坏键在内存中被替换为空默认值；正常 JSON 备份有只读保护检查，报表导出没有统一检查。只禁止写入不足以保证报表数据完整。
- 实测：损坏订单原始字符串后，真实 Electron 页面处于只读保护状态，但设置页仍成功保存 5,443 字节的零订单 Excel。API 同样生成空 CSV、空明细、合计 0 的 XLSX。
- 影响：损坏数据可能被误解成没有销售或金额为零，形成错误对账依据；其他未损坏模块还可能输出局部数据。
- 建议：所有正常报表统一检查存储完整性；只读保护时禁用并解释原因，仅允许明确标识的原始数据抢救导出。

### R04 [P2] 有效的小数数量、单价在打印和图片中改变，导致账面算式不成立

- 位置：`webapp/js/util.js:39–45`、`webapp/js/views/order.js:272–283`、`webapp/js/views/print.js:137–139`、`:236–238`、`webapp/js/views/bill.js:52–54`。
- 触发：按重量等方式录入超过两位小数的数量，或超过两位小数的单价。当前输入和数据校验允许这些值。
- 原因：`fmtNum()` 将数量固定四舍五入到两位，`fmtMoney()` 把单价当两位金额显示；金额计算却使用原值。
- 实测：`0.001 × 100 = 0.10` 在打印 HTML 中成为数量 `0`、金额 `0.10`；`100 × 0.125 = 12.50` 显示为 `100 × 0.13`，金额仍为 `12.50`。Canvas 和账单使用相同格式化函数。
- 影响：打印/PDF/图片与原始数据、Excel 不一致；收货和结算时无法按展示值复核。
- 建议：分别定义数量、单价、最终金额的精度。支持的精度必须贯穿录入、存储及所有输出；若限制为两位，应在保存前明确校验，不能只在输出时舍入。

### R05 [P2] 账单预览已应用的备注没有进入 Excel

- 位置：`webapp/js/views/bill.js:61`、`:73`、`:101–118`；快捷导出在 `webapp/js/views/stats.js:25–41`。
- 触发：编辑账单备注、应用修改后导出 Excel。
- 原因：预览使用 `st.note`，导出只构造标题、表头、明细、合计；没有传递或生成备注。页面标签却说明备注会在打印/导出底部显示。
- 实测：真实 Electron 页面预览出现“次月5号前付款”，对应 Sheet XML 完全没有该文字；修改后的标题则正常保留。快捷账单导出也没有读取默认备注。
- 影响：结算要求等说明在导出的客户账单中丢失。
- 建议：统一三种账单 Excel 的数据模型，支持合计后的备注区域，并验证预览、打印、Excel 一致。

### R06 [P2，文件覆盖风险] 分享同名单据图片会无提示覆盖旧文件

- 位置：`webapp/js/views/print.js:295–296`、`main.js:764–772`。
- 触发：同一单据分享后修改内容，再次分享；或两个导出名经文件名清理后相同。
- 原因：分享路径固定，文件名只包含单号，直接 `writeFile(target, buf)`，没有覆盖确认或冲突处理。
- 实测：连续两次调用真实分享 IPC 处理器，同一输出路径的 `old image` 被 `new image` 替换。
- 影响：之前留存的分享图片会消失。如果产品明确规定该目录只保存最新版，这是需说明的行为；如果用于留档，应修复。
- 建议：明确最新版/历史版本规则；需要留档时加时间戳或递增后缀，或者给出覆盖确认。

### R07 [P2，CSV 解释风险] 文本字段可原样输出为公式

- 位置：`webapp/js/store.js:796–801`、`:816–817`、`webapp/js/views/stats.js:274–275`。
- 触发：客户名、品名、备注、制单人等文本以 `=` 等公式前缀开头。
- 原因：CSV 转义只处理分隔符、引号和换行，没有文本单元格类型，也没有公式前缀防护。
- 实测：合法订单的客户名称 `=1+1` 在 CSV 中原样输出为 `,=1+1,`。本次未实际调用 Excel/WPS 执行公式，不把外部软件的执行结果作为已测事实。
- 影响：用启用自动类型/公式解析的表格软件打开时，文本存在被解释为公式的风险；CSV 加普通双引号并不能定义单元格为文本。
- 建议：对业务文本列制定安全导出策略，或优先使用带明确字符串类型的 XLSX；金额及数量列仍保留数字语义。

### R08 [P2] CSV 漏掉单独回车字符的引用处理

- 位置：`webapp/js/store.js:796–798`。
- 触发：从历史备份恢复的品名/备注含单独 `\r`，而非 `\r\n` 或 `\n`。
- 原因：引用判断只有 `/[",\n]/`，没有 `\r`。存储字符串字段没有禁止该字符。
- 实测：`A\rB` 原样输出为未加引号的 CSV 字段；本项目 CSV 解析器又会把该 `\r` 规范化成换行，导致记录边界改变。
- 影响：导出文件经再次处理时可能错行、列数不正确。
- 建议：引用规则覆盖 `\r`，增加逗号、引号、CR/LF、前后空白等内容的导出再解析测试。

### R09 [P2] XLSX 字符串含控制字符时生成无效 XML

- 位置：`webapp/js/xlsx.js:11–14`、`:142`；字符串备份校验在 `webapp/js/store.js:749–758`。
- 触发：备份中的商品名称等字符串包含转义控制字符，例如内部 `\u000B`。JSON 文本可正常解析，业务层当前接受它。
- 原因：XML 转义仅替换五种符号，未处理 XML 1.0 不允许的控制字符。
- 实测：恢复包含上述名称的商品后导出，`sheet1.xml` 留有实际 `0x0B`；用 .NET XML 解析器读取时明确报 invalid character。
- 影响：文件虽然保存成功，工作表 XML 却无效，读取程序可能报错或尝试修复；本次没有在 Excel/WPS 中测试其具体修复表现。
- 建议：按 SpreadsheetML 规则编码，或在导出前拒绝并指出问题记录；仅做 `&`/`<` 的 HTML 风格转义不够。

### R10 [P2] 搜索输入后立即导出，会使用上一个关键词

- 位置：`webapp/js/views/orders.js:98`、`:106–110`。
- 触发：输入或修改关键词后，在 200ms 防抖完成前点击导出。
- 原因：关键词只在定时器内写入 `st.kw`，导出直接读取旧状态。
- 实测：已有 `MATCH`、`OTHER` 两张单据，输入框值为 `MATCH` 时立即触发导出，输出仍含两张单据，`st.kw` 还为空。
- 影响：导出范围超出用户输入的筛选条件，尤其可能把其他客户单据一起导出。
- 建议：输入时立即更新状态，只对列表渲染防抖；导出前也可同步输入框并取消待执行任务。

### R11 [P2] 按日快照判断实际始终失效，历史备份很快被轮换

- 位置：`lib/data-store.js:135–150`。
- 触发：同一天持续修改数据并触发多次备份。
- 原因：`lastDated` 保存完整文件路径，却用 `lastDated.slice(0,8)` 与 `YYYYMMDD` 比较；普通路径开头不是日期，因此每次都进入创建分支。同秒只是复用文件名，不同秒就会新增。
- 实测：模拟同一天连续 12 秒的保存，生成每秒快照并触发保留数量上限，较早快照已被淘汰；目录只剩最近 9 个历史快照和 latest。
- 影响：原本代码意图的每日历史窗口退化为近期若干次保存，较早的可恢复版本更快消失。
- 建议：单独保存日期值，或从文件 basename 提取日期；历史快照与 latest 分别统计保留量。

### R12 [P2] 自动恢复把历史快照也识别成普通数据键

- 位置：`lib/data-store.js:98–105`、`:200–209`。
- 触发：主数据目录为空，从包含时间快照的外部目录自动恢复。
- 原因：排除快照的条件要求名称以 `data-` 开头，同时又用以数字开头的 `^\d{8}-\d{6}\.json$` 匹配完整文件名，两个条件无法同时满足。
- 实测：恢复后除了 `sd_v1_orders` 等正常键，还出现 9 个 `data-20261112-...` 数据键，其值是完整历史快照 JSON。
- 影响：快照被作为业务键重新写入主目录和下一份聚合备份，增加体积与递归嵌套，恢复/备份越用越重。
- 建议：修正为匹配完整名称的表达式，或只读取允许的数据键文件；增加恢复后的键集合断言。
